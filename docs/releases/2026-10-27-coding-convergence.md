# 2026-10-27：Coding 编辑收敛控制修复

修复 seeded Coding 连续编辑、未提交就绪声明，导致没有额度交接给验证和审查的问题。
服务端在编辑或调用额度边界停止继续编辑，进入原有强制检查，再执行实验和 Reviewer。
本轮只执行免费验证，不新增真实 LLM/Tavily 请求，不改变 v6 的失败记录。

## 行为变化

- 每次完整源码请求携带累计编辑数、剩余编辑数、共享模型调用余额和后续流程预留额度。
  文件写入预览使用写入后的计数，继续遵守完整源码及原请求体上限。
- 自动工作流至少为 Reviewer 预留一次调用；仍可重规划且余额足够时，预留审查、
  一次重规划和最终审查三次。余额较低时保留必要审查，最小三调用工作流仍可完成。
- 达到现有八次编辑上限，或触及后续调用预留边界时，成功的单次写入交给强制静态检查
  和 pytest。交接原因保存在验证记录中；不会伪造模型提交 `submit_code_ready`。
- Snapshot 模式的批量原生调用在任何文件写入前整体拒绝，最多纠正一次，并把反馈传入
  下一次源码快照。普通非 Snapshot Coding 的已有工具批处理保持兼容。
- 未解决的文件/协议错误不能通过自动交接。静态检查和 pytest 均须成功、退出码为零且
  输出完整；检查期间源码变化也会失败。检查失败且无可用编辑额度时停止，不额外消耗修复次数。
- 实验、独立产物核验和 Reviewer 仍然执行。回归包含真实需求未满足的例子，证明即使
  静态检查及 pytest 通过，Reviewer 仍可拒绝完成任务。

预算为 12 次调用且研究等步骤已用 5 次时，保留后续 3 次，Coding 最多再调用 4 次后进入检查。
这仍是原预算内分配，不扩大总调用、token、编辑、沙箱或训练上限。
有限额度不能保证任意复杂的修改都能完成；源码不完整或检查失败仍保留失败。

## 验证

独立 main 工作树完整回归 **483 passed、3 skipped**；Ruff 与 mypy（184 个文件）通过。
定向回归 **61 passed**，覆盖普通 Coding 兼容性、快照批处理、额度交接和请求预检。
main 验证显式指定独立目录的源码路径，并逐文件比较所提取的两份运行时代码与测试。
三个跳过项为未开启的旧 Compose smoke 与两个 Windows 符号链接权限限制。
本次 main 同步以独立工作树回归和免费 Docker 证据为依据，dev 评测工具兼容性回归另行记录。

免费 Docker 验证包含四种预期结果：
